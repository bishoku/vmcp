# REST APIs as MCP tools

vMCP v0.1.0 adds REST API upstreams alongside existing MCP upstreams. Define operations manually or import an OpenAPI/Swagger document, select the operations to expose, and publish them through the existing virtual-server and agent-access model.

## Highlights

- REST operations with validated JSON request/response schemas, path/query parameters, response-field selection, timeouts, and explicit execution tests.
- Basic Auth, bearer tokens, OAuth2 Client Credentials, operator-configured headers, and opt-in forwarding of verified agent identity. Secrets remain encrypted and participate in key rotation.
- OpenAPI 3.0/3.1 and Swagger 2.0 import from JSON/YAML files or pasted definitions. Preview operations and compatibility warnings before adding selected operations to a draft; the existing save flow remains authoritative.
- Existing authorization, policy, audit, PII masking, TLS and egress protections remain in the execution path. Import never fetches external references or automatically applies credentials and server settings.

## Reliability and scale

- Prevent automatic replay of REST operations after a lost HTTP/1.1 or HTTP/2 response, including requests carrying idempotency headers, while preserving connection pooling.
- Reuse unchanged prepared REST schemas across configuration snapshots, avoiding repeated compilation without weakening freshness or revocation checks.
- A local two-node acceptance run covered 300 REST upstreams, 300 virtual servers, 60,000 tools, 600 sessions, load spikes, configuration propagation, node loss and rejoin. All declared acceptance thresholds passed; 105,702 successful calls matched durable audit records, with zero duplicate upstream executions.
- At 200 calls/s, p95 latency was approximately 46 ms. The 600 calls/s spike completed approximately 585 calls/s; 285 scheduled requests were not submitted. Configuration propagation completed in 2.35 seconds. Node loss left one operation with an unknown outcome; it was not replayed.

These are local synthetic-service results, not a capacity guarantee for production REST services or identity providers. See the [acceptance report](https://github.com/bishoku/vmcp/blob/v0.1.0/benchmark/results/rest-release-20261020/README.md) for thresholds, resource usage and limitations.

## Upgrade notes

1. Back up PostgreSQL and apply migration **28** before starting the updated control and data planes.
2. Upgrade **all** control/data-plane nodes before configuring REST upstreams; older nodes do not understand this upstream kind.
3. Existing upstreams retain their MCP kind. Existing MCP configuration and execution flows remain supported.

Rolling back migration 28 drops REST configuration columns. Do not assume a lossless database rollback after creating REST upstreams. A timeout or node loss does not prove that a REST write failed; reconcile the upstream service state before manually retrying.

The initial REST adapter supports JSON operations with GET/POST/PUT/PATCH/DELETE, scalar path/query parameters, and up to 200 operations per upstream. Unsupported import constructs are reported before selection. Authentication and the base URL must be reviewed separately. OAuth token endpoints use system trust; custom service TLS settings do not configure token-endpoint trust. See [REST upstream configuration and import limits](https://github.com/bishoku/vmcp/blob/v0.1.0/docs/Upstreams.md).

## Validation

Local validation passed 500 Go tests with race detection and no skips, 179 UI tests, 120 browser tests, OpenAPI checks, migration preservation tests, and MCP/REST acceptance smoke tests. GitHub CI additionally passed core/web checks, image security scanning, and a real Helm installation/upgrade before tagging.
