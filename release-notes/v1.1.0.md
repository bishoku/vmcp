# Teams, projects and upstream tool approvals

vMCP v1.1.0 adds externally managed team ownership, projects and cross-team tool approvals. This is a **minor release**: existing installations remain in the Default/unmanaged workspace with their endpoint URLs, keys and tool selections preserved. Managed ownership is an explicit administrative choice; assigning an owner enables the corresponding access restrictions.

## Team and project governance

- Platform admins map teams to an exact trusted OIDC issuer and group claim value. Membership stays in the identity provider; vMCP does not introduce local user management.
- Each upstream has one owner team or remains unmanaged. Each project has one owner team or remains unmanaged; a project can contain multiple virtual MCP servers, which inherit its ownership.
- A team can own both upstreams and projects. Team members manage their own resources; platform admins manage mappings, projects and ownership transfers.
- Cross-team exposure of an upstream tool requires approval from its owner, scoped to the consuming virtual server. Unmanaged upstreams remain outside this approval flow. Same-team access is allowed unless explicitly rejected or revoked.
- The management UI, REST API and export/apply support ownership and grants. The data plane applies approvals in its configuration snapshot without an ownership query on every tool invocation.

## Upgrade and compatibility

Migration **33** creates teams, projects and tool grants, assigns existing virtual servers to Default, and leaves existing upstreams unmanaged. Back up PostgreSQL and follow the chart's migration-before-rollout procedure. Existing global viewer/editor permissions continue to apply to unmanaged resources; they do not override explicitly assigned team ownership.

Existing sessions must sign in again to gain new team-scoped rights. Team claims expire after 15 minutes and require fresh authentication; this is not instantaneous LDAP/SCIM synchronization. Once teams exist, tenant-wide export/apply requires platform admin. Review automation permissions before enabling managed governance. Omitting governance arrays from apply preserves them; omitted ownership fields preserve existing assignments on update.

Ownership transfers revoke affected explicit grants and recalculate implicit access. Review approvals before transferring resources. Cross-team resources, prompts, subscriptions and upstream instructions are not covered by tool grants; they require same-team or unmanaged ownership. Team/project deletion and archival, project-scoped GitOps, semantic search and dynamic registry discovery are not included.

The Helm chart advances to **1.1.0**, application tag to **v1.1.0**, and OpenAPI document version to **1.1.0**. Runtime API paths remain `/api/v1`. Benchmark memory settings described below do not change production Helm defaults.

## Performance acceptance and known limitation

A ten-minute MicroK8s run with **60,000 tools, one data-plane, 8 CPU limit, 4 GiB Go memory target and 6 GiB container limit**, through NodePort/CNI, passed the agreed acceptance thresholds:

- 999.85 successful TPS at a 1,000 TPS target; 99.995% success.
- p95 81.3 ms, p99 107.8 ms.
- Sampled peak RSS 1.82 GiB and container usage 1.84 GiB; no data-plane restart/OOM.
- Dedicated key revocation under load returned its first 401 in 3.425 seconds, with readiness healthy.
- No missing audit operations, duplicate executions or invalid results.

**This run was not error-free:** 30 of 599,982 submitted traffic calls returned JSON-RPC `-32603` in the second when the revocation snapshot was published. The global revision guard can stop calls using an older snapshot even when another key changed; the stream layer can surface that rejection as a generic MCP error. Timing and code inspection support this explanation, but per-call internal audit reasons were not archived for all 30 errors. The error rate was within the agreed 0.1% budget. This release does not claim disruption-free configuration updates and does not disable reauthorization or add automatic tool retries.

The earlier intermittent NodePort connection refusal did not recur in this run; its root cause is not proven resolved. These are synthetic workload results on one host, not a general maximum-TPS or production-sizing guarantee. Memory/GC behavior, failed runs, capacity limits and reproduction details are preserved in the benchmark reports.
