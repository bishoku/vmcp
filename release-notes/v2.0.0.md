# Explicit authorization and scoped audit access

vMCP v2.0.0 makes granular control-plane authorization mandatory. This is a
breaking release: coarse role labels and team membership no longer grant implicit
configuration or audit access. Helm chart and OpenAPI versions are 2.0.0.

## Changes

- Explicit resource and field permissions, scoped role assignments and verified
  OIDC claim mappings use deny-by-default decisions. Platform administrator
  identity remains distinct from assignable roles, including PlatformOperator.
- Audit access follows immutable ownership periods. Metadata, identity/details,
  request payloads and response payloads have separate permissions. Historical
  records without ownership context require explicit legacy audit permissions;
  current ownership does not retroactively grant access.
- Browser sessions store verified identity/claims encrypted in shared PostgreSQL.
  Revocation and logout work across control-plane replicas. The UI uses server
  capability decisions, sends narrow PATCH updates, and clears drafts on expiry.
- Strict audit writes use batched inserts in the same durable transaction,
  preserving atomicity, replay protection and ownership/payload association.
- Omni preview distinguishes runtime credential rejection from console access
  denial. README diagrams describe Omni, MCP/REST upstreams, optional models,
  identity integrations and independent audit exporters.

## Breaking API and identity changes

- Legacy/shadow authorization modes are removed; there is no compatibility switch
  or automatic import of old coarse roles. `GET /api/v1/access/status` replaces
  `/api/v1/access/migration-status`. Mode/readiness fields removed from access and
  capability responses must no longer be consumed by clients.
- Control-plane token scope `read` now identifies an assignment-based non-admin
  principal, not automatic GET access. Explicit assignments may authorize writes.
  `admin` remains platform administrator identity. Agent OAuth bindings and
  control-plane OIDC mappings are separate trust boundaries.
- Existing browser sessions require sign-in again. Mapping-derived access expires
  after at most 15 minutes, bounded by verified ID-token expiry; users may need
  to sign in again. Cookie-authenticated writes require `X-VMCP-CSRF: 1`.

## Installation and upgrade

New installations should use the v2 chart and immutable image overlay, establish
bootstrap administrator access, then explicitly configure non-admin roles,
assignments and trusted issuer mappings. See the
[release installation guide](https://github.com/bishoku/vmcp/blob/v2.0.0/docs/Release-Installation.md).

For an existing installation:

1. Review migrations **36–42** and test against a restored database copy. Back up
   PostgreSQL, deployed values and Secrets, preserving the encryption master key.
   Inventory UI, automation, GitOps and IdP identities and their required scopes.
2. Schedule a maintenance window; stop old application writers and traffic before
   migration. Apply all pending migrations through 42 using the migration image.
   The chart runs a blocking pre-upgrade migration Job when enabled; provision its
   credentials first. Do not operate mixed v1/v2 writers or assume zero downtime.
3. Deploy matching v2 images and chart values. Confirm bootstrap recovery access
   before relying on SSO. Configure explicit assignments/mappings, sign in again,
   and validate allowed and denied actions for each non-admin identity.
4. Verify direct/Omni calls, upstream credentials, audit metadata/payload boundaries,
   exporter delivery, cross-replica logout and grant revocation before reopening
   traffic. The local acceptance drill does not certify your IdP/Secret distribution.
5. Helm rollback does **not** reverse database migrations. Old binaries alone are
   not a recovery plan. Down migrations can discard new policy/session/provenance
   data; use a tested database restore with matching binaries, values and keys.
   See [security recovery](https://github.com/bishoku/vmcp/blob/v2.0.0/docs/SECURITY_OPERATIONS.md).

## Validation and limits

The selected local acceptance profile passed: 60,000 tools, one data plane,
8 CPU, 4 GiB Go memory target, 6 GiB pod limit, strict ownership-aware metadata
audit and 1,000 calls/s for 600 seconds. It achieved 999.6 successful calls/s,
99.973% success, p95 168.8 ms and p99 366.1 ms. There were 164 steady errors and
8 dropped requests; all 600,078 successful calls matched durable audit records,
with no duplicate executions or incomplete operations. Loaded revocation took
3.761 seconds; peak RSS was 2.03 GiB with no OOM/restart.

The workload used MCP calls backed by REST fixtures. This is not a 2,000 calls/s
peak, native MCP-upstream fault/soak, control-plane throughput or production SLA
claim. Authorization acceptance passed 66 checks with a real local IdP and two
control-plane processes. Regression evidence includes backend race/integration,
frontend unit/browser, image-security and Helm installation/upgrade checks.

See the [acceptance assessment](https://github.com/bishoku/vmcp/blob/v2.0.0/maintainer/ISSUE31_ACCEPTANCE.md)
for failures and limitations. Detailed benchmark artifacts stay local; only
reviewed aggregate results are retained in the repository. vMCP remains beta.
