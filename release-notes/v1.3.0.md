# Conversation-aware audit and Omni caller metadata

vMCP v1.3.0 adds optional client-specific conversation correlation to agent keys
and fixes caller metadata forwarding through Omni invocation. Existing clients
without correlation metadata continue to work. Chart and OpenAPI versions are 1.3.0.

- Omni `invoke_tool` preserves outer `params._meta` in the virtual MCP call.
  Business arguments remain separate. Existing upstream Caller context rules
  continue to select allowed fields for MCP metadata or REST headers.
- Agent keys support optional JSON Pointer mappings for conversation, root
  conversation and turn IDs. The editor includes an Antigravity preset. Rotation
  preserves the mapping; empty configuration disables it. Missing or invalid
  optional correlation values never block tool execution.
- Audit correlation follows direct virtual MCP calls and all four Omni tools,
  including explicitly linked virtual/upstream/model child events. Group keys
  are scoped to immutable agent-key identity. Root and child conversation IDs
  remain separately searchable; turn IDs are optional and never inferred.
- **Audit Log → Conversations** provides server-aggregated, paginated summaries
  with existing access restrictions and drill-down to operation trees. Exact
  conversation/root/turn/group filters are also available on raw events.
- Omni keeps transient execution sessions. This release does not introduce
  persistent Omni transport sessions, upstream session reuse or progress relay.

## Actions for existing installations

1. Back up PostgreSQL and retain the existing Helm values, Kubernetes Secrets and
   master key. Run **migration 35 (`00035_audit_conversations.sql`) before updated
   control/data planes or other audit writers**. It adds key configuration, audit
   metadata columns and three partial indexes. The chart's pre-upgrade migration
   Job performs this when automatic migration is enabled. For a large audit table,
   allow a maintenance window: index creation can wait for/block concurrent writes.
2. Upgrade the matching application images using this release's chart and
   `helm-images.yaml`. Keep existing database, Redis, Keycloak, ownership, upstream,
   model and credential settings. Pause Omni traffic until the new data-plane and
   Omni are both ready; do not leave a mixed-version deployment serving calls.
   Helm rollback does not undo database migrations. Rolling migration 35 back
   removes new correlation/mapping data while preserving original audit/key rows.
3. Existing/new agent keys default to extraction disabled. Configure **Agent key →
   Edit → Audit correlation**, or PATCH `auditCorrelation` with JSON Pointers
   relative to `params._meta`. Omission preserves a mapping; `{}` clears it.
   No new environment variable or client metadata namespace is required. OAuth
   bindings and anonymous calls continue without conversation extraction.
4. Selected IDs are searchable **audit metadata even when payload capture is off**.
   Use non-sensitive opaque identifiers. Payload masking does not mask these
   indexed columns. Existing payload retention, encryption and upstream Caller
   context forwarding policies remain separate. Review SIEM schemas if they reject
   additive metadata fields in exporter envelopes.
5. Validate a real client call with its existing `_meta`, inspect **Conversations**
   and follow **View operations**. Metadata-free calls remain in Operations/Raw
   events. For MCP upstreams, only configured Caller context fields are forwarded;
   forwarding `progressToken` does not gain progress support in Omni.

## Performance validation

Before/after tests used direct virtual MCP calls on an isolated MicroK8s namespace:
500 TPS for five minutes each, 6,000 tools, one data-plane, strict metadata audit,
4GiB Go memory target and 6GiB pod limit. Mapping was enabled for the after run.
Both passed: successful TPS ~499.94, zero tool/HTTP errors; two of 150,000 scheduled
requests were not sent by the after-run load driver. p95 increased 52.93 → 58.74ms,
p99 69.59 → 79.16ms; median CPU +1.4%, RSS +4.35%. WAL throughput increased ~30.7%
and total synthetic database size ~44.5%, chiefly reflecting additional audit
metadata/index writes. No material GC pause increase was observed. A single pair
of runs is not a maximum-capacity or statistical-significance claim.

See [configuration and upgrade details](https://github.com/bishoku/vmcp/blob/v1.3.0/docs/Audit-Conversation-Correlation.md)
and the [performance report](https://github.com/bishoku/vmcp/blob/v1.3.0/benchmark/results/conversation-correlation-500tps-20261030.md).
