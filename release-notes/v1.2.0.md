# Optional Omni MCP discovery gateway

vMCP v1.2.0 adds an optional Omni MCP process exposing `discover_server`,
`discover_tools`, `get_tool_schema` and `invoke_tool`. Agents can discover tools
by intent and fetch schemas on demand through `/mcp/v1/omni`, using their existing
runtime keys or OAuth identity bindings. Direct vMCP endpoints remain unchanged.
This is a **minor release** with an additive, opt-in feature.

## Discovery and authorization

- Explicit per-vMCP publication; migration 34 leaves every existing vMCP unpublished.
- Hybrid semantic/keyword search with an explicitly configured OpenAI-compatible
  embedding service, including self-hosted models. No implicit external provider.
- Fresh data-plane authorization before/after search and before schema/invocation;
  team ownership, tool approvals, IP restrictions, key revocation and existing
  invocation limits remain authoritative. A stale index cannot preserve access.
- Original runtime identity, target and trace retained in audit. Schemas and
  execution results remain in the data plane; Omni holds searchable metadata/vectors.
- Explicit keyword fallback when embeddings are unavailable; no automatic write retry.

## Console and deployment

The Omni page provides endpoint configuration, admin index status/refresh and
runtime-credential search/schema preview. Virtual server editors include an
opt-in publication switch. Teams and Projects screens now use the established
list, editor and ownership-selection UI patterns.

New multiarchitecture image: **`barishoku/vmcp-omni-mcp:v1.2.0`**. Helm keeps Omni
disabled by default; enabling it creates the workload, private bridge secret and
exact public MCP routes. Docker, Compose and native process setup, environment
variables, OAuth, proxy rules and upgrade steps are documented separately.
The chart is **1.2.0**, app tag **v1.2.0**, OpenAPI version **1.2.0**; API paths remain `/api/v1`.

## Acceptance evidence

A ten-minute isolated MicroK8s run at **1,000 tools / 100 TPS** completed all
**60,000 Omni invocations** successfully (p95 20.70 ms, p99 24.50 ms). Separate
100 TPS discovery traffic increased direct-path latency but stayed within the
agreed gates. Key, grant and publication revocation propagated in about 105–107ms.
Embedding/Omni/data-plane outage and restart checks passed.

The additional search workload returned 59,864 hybrid and 140 keyword-fallback
responses; this is not a guarantee of uninterrupted 100 semantic searches/s.
The CPU-based embedding provider was the largest resource cost and its concurrency
limit reproduced HTTP 429s in a separate diagnostic. Model/provider sizing remains
independent of the small Omni pod. See [full acceptance results and limitations](https://github.com/bishoku/vmcp/blob/v1.2.0/benchmark/results/omni-1000-100-20261027.md).

## Compatibility and limits

Apply migration 34 before deploying the new binaries; preserve the existing DB
and master key. Normal vMCP operation does not depend on Omni availability.
Omni is synchronous stateless Streamable HTTP: no resources/prompts, server-driven
callbacks, resumable streams or async tasks. Native MCP calls create isolated
transient upstream sessions. Indexes and discovery quotas are per replica.

Omni and DP are one logical OAuth resource; independent-audience token exchange
is not included. Search relevance depends on the chosen model and tool metadata;
the synthetic bilingual acceptance corpus is not a production-domain guarantee.
The existing global snapshot revision guard can reject in-flight calls during a
configuration refresh, including changes to unrelated keys. Reauthorization stays
enabled and tools are not automatically retried.
