# Configurable encrypted audit payloads

vMCP v0.1.2 adds optional request and response payload capture with encryption, configurable masking, independent retention, and per-consumer export controls. Payload capture is disabled by default.

## Highlights

- Configure strict or relax audit mode and request/response capture for virtual calls, upstream calls, management APIs, discovery/system work, and API reads in Settings.
- Add global, virtual-server, and upstream RE2 masking rules. Local rules add to mandatory secret filters and global protection. Preview unsaved policies against sample JSON without persisting the samples.
- Store masked payloads encrypted and separately from metadata. Administrators can load payloads on demand from audit details; payload access is itself audited without recapturing the returned content.
- Pin the policy revision and durability mode for each operation. Strict mode waits for durable storage; relax mode uses a bounded asynchronous queue and can lose records during overflow, failures, or shutdown.
- Link upstream protocol exchanges to their parent operation and request. Capture REST method, path, query, body, response status, and bounded response content without authorization headers or credential-acquisition traffic.
- Opt individual export consumers into payload delivery. Encrypted delivery snapshots preserve the same payload bytes across retries and expiry. Secret rotation includes stored payloads and pending export snapshots.
- Export and apply audit settings with declarative configuration. Interactive settings updates reject stale revisions.

## Security and retention

- Apply secret-field filtering to JSON objects and arrays encoded inside strings, including MCP text copies of REST results. Embedded JSON shares traversal limits and retains its outer string type; regex matches on the original encoded JSON redact that entire string.
- Preserve metadata while its payload awaits cleanup, so shorter metadata retention cannot delete an unexpired payload through cascading deletion. Legal holds and pending payload exports can extend retention.
- Require Go 1.27.3 and use the matching Docker build image to address the crypto/x509 issue reported as GO-2026-6809 by release CI.

## Upgrade notes

1. Back up the database and apply migration **29 (`00029_audit_payloads.sql`)** before deploying the new binaries. Apply the additional table grants documented in `deploy/postgres/audit-roles.sql` to existing database roles.
2. Update the control plane, data plane, web UI, exporters, and secret rotation utility. Keep payload capture disabled until every writer and exporter has been updated; older versions do not enforce these policies.
3. Payload exporters require `VMCP_MASTER_KEY` and the applicable keyring/tenant configuration. Metadata-only exporters can continue without a key. Explicitly enable payload delivery for each intended consumer.
4. Review capture scopes, masking rules, and retention before enabling capture. The default payload retention is seven days and the default stored payload limit is 64 KiB. Capture and masking policies apply to new operations; they do not rewrite historical payloads.

An empty audit mode keeps the deployment default: strict on the control plane and `VMCP_AUDIT_MODE` on the data plane (`best_effort` remains an alias for relax). Pending/dead export snapshots and legal holds may retain encrypted content beyond normal expiry. Destination retention must be managed separately.

Downgrading migration 29 drops payloads, settings, and saved export envelopes. Archive required evidence and coordinate a maintenance window before rollback. See the [audit guide](https://github.com/bishoku/vmcp/blob/v0.1.2/docs/Audit-Log.md) for operational details.

## Validation

Regression tests cover embedded JSON secret filtering and traversal limits, payload export masking, payload retention independent of metadata age, and policy pinning across a real revision change. Release CI runs Go race and integration tests, vulnerability scanning, frontend build/lint/unit/browser tests, and Helm installation/upgrade checks on a disposable cluster. Multi-platform image publication is gated on that CI before the GitHub release is published.
