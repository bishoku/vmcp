# Fixed REST parameters and fallback values

vMCP v0.1.8 lets REST operations send fixed path/query parameters without exposing them as MCP arguments, and apply configured defaults when optional arguments are omitted.

## Highlights

- Configure **Expose to MCP** and **Use default value** in the operation modal's Parameters section. Hidden parameters require a fixed value; exposed parameters can use a fallback or remain caller-supplied.
- Keep fixed parameters out of the advertised MCP input schema and reject attempts to supply them as tool arguments before dispatch. A configured default makes an exposed parameter optional, including path parameters.
- Resolve values consistently in request preview and actual REST execution. Apply defaults only to absent arguments; preserve explicit zero, false, and empty strings. Invalid supplied values fail validation rather than falling back.
- Validate configured values against their full scalar schemas, including types, enums, patterns and numeric bounds. Reject unsafe configured path values using the same rules as caller-supplied paths.
- Retain query URL encoding and numeric precision in backend mapping. Numeric fields in the editor preserve intermediate input and reject unsafe integer conversion.
- Verify API create/update/export/import, runtime snapshot invalidation, real virtual MCP requests, preview/execution agreement, and mobile/desktop modal persistence.

## Upgrade notes

- **No new database migration is introduced.** Installations upgrading from v0.1.7 already have the required schema. Older installations must apply existing migrations through **31**.
- **Update every control-plane and data-plane instance before using these settings.** Older binaries do not enforce fixed values or apply fallbacks. Update the web UI and refresh clients' `tools/list` after saving parameter changes.
- Existing parameters remain exposed when `exposeToMcp` is omitted. `defaultValue` explicitly activates substitution; an existing or imported `schema.default` remains an annotation and does not change runtime behavior by itself.
- A configured default satisfies the parameter's requirement. Removing it restores the existing required setting; path arguments without defaults remain required. Hidden parameters always require a fixed value.
- These settings apply to scalar path/query parameters, not request-body properties. Null, object, and array defaults are not supported.
- Keep the operation path as `/sample` and define query parameters separately. For example, hide `type` with fixed integer value `1`, and expose `content` with fallback `all`; `{}` then produces `/sample?content=all&type=1`.

See the [fixed parameters and fallback values guide](https://github.com/bishoku/vmcp/blob/v0.1.8/docs/Upstreams.md#fixed-parameters-and-fallback-values) for configuration examples and behavior.
