# Invocation security and two user identity models

vMCP v2.0.1 adds upstream/tool step-up authentication and operation approval.
Helm chart and OpenAPI versions are 2.0.1.

**Breaking configuration change:** the global `VMCP_APPROVAL_URL` hook is removed.
A data plane with that variable set refuses to start. Despite the patch version,
this is not a transparent upgrade for deployments using the old hook.

## Changes

- Select `oauth_subject` when the gateway token identifies the user, or
  `caller_context` when a shared application credential carries separately
  verified customer/session context. Existing gateway access bindings remain in
  force; there is no automatic fallback between user identity sources.
- Configure step-up and approval independently at upstream/tool scope. Inherited
  requirements cannot be weakened. External services verify customer sessions and
  consume operation-specific approvals before dispatch. PostgreSQL reservations
  prevent repeated admission across gateway replicas.
- Manage encrypted service credentials and policies through the API and UI.
  Portable export/apply omits secrets and resolves upstream slugs. Secret rotation
  includes invocation service credentials. Referenced upstreams cannot be deleted
  until their invocation policy is removed.
- Preserve OAuth assurance challenges on direct and Omni routes, including MCP
  errors after streaming starts. Audit payloads mask caller/session metadata.
- Add an isolated source-built Keycloak OTP lab and browser MCP client with both
  identity modes, approval/rejection, customer isolation, resources, prompts and
  completion examples.
- Fix CVE-2026-78661 (`golang.org/x/net`) and GO-2026-6865
  (`github.com/klauspost/compress`).

## Upgrade from v2.0.0

1. Back up PostgreSQL, deployment values, Secrets and encryption keys. Test the
   upgrade against a restored copy. Inventory old approval-hook consumers and
   clients that need the new pending/step-up interaction contract.
2. Prepare a verification/approval service implementing the
   [version 1 contract](https://github.com/bishoku/vmcp/blob/v2.0.1/docs/Invocation-Security.md).
   Choose the correct user identity source, TLS/service credentials and explicit
   field allowlists. Do not substitute a caller-provided MFA flag for verification.
3. Stop old writers and affected runtime traffic for the transition. Apply
   migrations **43–44** with the matching migration image; Helm's blocking
   migration job does this when enabled. Migration 43 adds encrypted invocation
   settings and durable dispatch reservations. Migration 44 adds
   `invocation_security.read` / `invocation_security.manage` and grants them to the
   built-in Platform Operator role. Custom roles require explicit grants.
4. Deploy matching v2.0.1 components. Remove `VMCP_APPROVAL_URL` from data-plane
   configuration, then configure its replacement through the management API/UI
   **before reopening protected traffic**. Migration creates an empty policy;
   it does not translate the old hook or automatically protect any upstream.
   Do not run mixed old/new gateway writers when relying on the new enforcement.
5. Verify both allowed and denied calls, challenge handling, pending/approved
   operations, replay rejection, caller-context forwarding, export/apply and
   audit redaction. Reopen traffic only after policies are loaded by all replicas.
6. Helm rollback does not undo database migrations. Older binaries do not enforce
   the new policies. Down migrations discard policy/replay data and permissions;
   use a tested database restore with matching binaries, values and keys, keeping
   traffic stopped until equivalent enforcement is restored.

## Validation and known limits

The release adds a PostgreSQL upgrade regression from schema 42 with existing
upstream, caller context and custom access grants, plus restartable invocation
credential rotation coverage. Required CI includes Go race/integration and SDK
checks, vet, vulnerability scanning, web unit/browser tests, OpenAPI validation,
Helm install/upgrade, image scans and the two-mode OTP/approval lab.

The demo is development-only, source-built from the release checkout and is not
an additional published release image. Its verification/approval state is in
memory. An intermittent CI OAuth callback timeout is tracked in
[#42](https://github.com/bishoku/vmcp/issues/42); the same commit passed on a clean
rerun. This is not production HA, restore or performance certification.

Pending/step-up MCP errors are vMCP extensions and need client support. Admission
reservations do not provide an atomic business transaction with an upstream;
reconcile ambiguous executions before submitting a new operation. Reservations
have no automatic retention cleanup. vMCP remains beta.
