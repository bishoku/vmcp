# Per-call header mappings and clearer server configuration

vMCP v0.1.5 adds explicit HTTP request header mappings for MCP and REST upstreams, alongside a more organized server configuration experience.

## Highlights

- Select incoming HTTP headers per upstream and map each source name to an upstream target name. Matching source and target names forward values without renaming them.
- Support Streamable HTTP MCP, legacy SSE MCP, and REST tool calls. Values remain scoped to the current invocation, including concurrent calls sharing an MCP session; they are not attached to initialize, discovery, or background SSE requests.
- Mark mappings as required to reject missing or empty headers before dispatch. Optional missing headers are omitted, and multiple header values are preserved.
- Reject reserved transport, session, gateway authentication, and proxy identity headers on both sides of a mapping. Reject duplicate targets and conflicts with static upstream/operation headers or enabled REST caller-context mappings.
- Preserve mappings through API writes, declarative import/export, and runtime snapshot updates. REST previews display placeholders; required mappings are tested through actual MCP tool calls.
- Group upstream settings into connection and identity, security and shared headers, per-call context, and REST operations. Configure header mappings in a modal before saving the upstream draft.
- Align REST and MCP summary cards, organize virtual-server guidance and protection settings, and share the summary-card design with virtual-server details.
- Add reproducible header/metadata microbenchmarks and document their measured costs and remaining optimization opportunities. This release does not include metadata performance optimizations.

## Upgrade notes

1. Back up the database and apply migration **31 (`00031_request_header_mappings.sql`)** before deploying the updated services. Installations upgrading from releases before v0.1.4 also need migration 30 for caller context.
2. Update all control-plane and data-plane nodes and the web UI before configuring mappings. Older data-plane nodes do not implement the forwarding rules. Existing upstreams default to an empty mapping list.
3. Configure mappings under **Per-call context → Configure mappings**. Use **Use mappings** to add modal changes to the draft, then **Save** to persist the upstream. The API field is `requestHeaderMappings`: omission preserves existing rules; `[]` clears them.
4. Use dedicated application headers for upstream-validated user tokens. Gateway `Authorization` and cookies cannot be mapped. Token verification remains the upstream's responsibility; audit and log capture policies are unchanged.
5. Configure only trusted upstream destinations, including MCP fallback URLs. Retries and fallbacks for a tool invocation receive the same mapped values.

Up to 16 mappings are allowed. Header names are matched case-insensitively. Mapped values are limited to 8 KiB per target header and 32 KiB in total; caller metadata has its own separate 32 KiB limit. Large metadata objects, including many small unknown fields, can increase allocation and garbage-collection costs. See [request header mappings](https://github.com/bishoku/vmcp/blob/v0.1.5/docs/Upstreams.md#per-call-request-header-mappings) and the [performance measurements](https://github.com/bishoku/vmcp/blob/v0.1.5/benchmark/PERFORMANCE.md#per-call-header-and-caller-metadata-cost-2026-10-21).

Rolling back migration 31 removes the saved mappings. Disable mappings before reverting to older services, which do not enforce required-header rules.
