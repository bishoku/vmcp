# Tool composition, bulk approvals and external HTTPS quickstart

vMCP v1.2.4 improves tool composition and ownership workflows, and supports fresh
quickstart installations behind an external HTTPS proxy. No database migration
or breaking API change is required. Chart and OpenAPI versions are 1.2.4.

- Quickstart `--external-https` generates HTTPS public gateway/Omni URLs, Keycloak
  hostname, console callback/Web Origin, runtime issuer and demo team issuers.
  TLS terminates at the external proxy; internal connections and ingress remain
  HTTP. Use `--tls-secret` instead for ingress TLS. Existing Keycloak clients and
  team mappings remain create-only; this flag does not migrate previous installs.
- Virtual server tools distinguish missing requests from pending approvals.
  Request all missing approvals or explicitly select tools to request again;
  existing approved grants are preserved.
- Ownership queues support individual or server/upstream group selection for
  bulk approval, rejection and revocation. Consumer project/team and upstream
  owner metadata accompany review. Rejection and revocation require a reason.
- `POST /api/v1/tool-grants/bulk` accepts 1–200 items with independent ownership,
  version and audit checks, returning per-item outcomes for partial failures.
  Tool-grant mutation audit targets now retain their composite identities.
- The virtual server Tool picker combines Available/Shared tabs, starts without
  an upstream selection, supports collapsible groups and progressive listing,
  and adds all remaining or search-matching tools without duplicates. Exposed
  tools occupy the wider adjacent column; the picker starts collapsed on mobile.
- Team/project details, editors and related access dialogs use the same centered
  responsive modal component as other console screens.

Tool selection, saving and approval submission remain separate operations.
Approval decisions do not bypass runtime policies or grant clients access to
additional virtual servers. Clients must inspect partial bulk results and refresh
after conflicts rather than blindly replaying successful operations.

See the [quickstart guide](https://github.com/bishoku/vmcp/blob/v1.2.4/docs/HELM_QUICKSTART.md)
and [ownership workflows](https://github.com/bishoku/vmcp/blob/v1.2.4/docs/Teams-and-Projects.md).
