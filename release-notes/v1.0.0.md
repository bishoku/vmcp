# vMCP 1.0 — managed mock upstreams, clearer auditing and hardened delivery

Publication did not complete; use [v1.0.1](v1.0.1.md). The original tag is retained unchanged.

vMCP v1.0.0 adds a shared WireMock-backed mock upstream workflow, separates audit activity by origin, reduces PostgreSQL delivery contention and hardens the container release pipeline.

## Managed mock upstreams

- Create and manage multiple mock REST upstreams through the control plane and web UI using one operator-managed WireMock instance. Existing REST-to-MCP mapping publishes mock operations through virtual MCP servers.
- Use the quick operation editor and visual request/response rule editor for common cases, or edit supported WireMock JSON for advanced matching and dynamic response templates. Draft edits remain separate from saved configuration.
- Synchronize managed mappings, inspect provider status and reconcile changes through the control plane. Mapping ownership and namespace prefixes keep separate mock upstream definitions apart without creating a pod per user.
- Mock support is optional. Configure `VMCP_WIREMOCK_URL` and explicit egress grants only when using it. WireMock's administration endpoint is internal infrastructure and must not be exposed as a public API. Arbitrary extensions, file access and unsupported WireMock capabilities remain restricted.

## Audit activity and operational visibility

- Filter Operations and Raw events by **Virtual MCP calls**, **Control plane API**, **System activity**, or **Upstream calls only**, with filtering applied before cursor pagination. Virtual/control filters include their explicitly linked upstream attempts.
- Stop recording routine discovery polling and subscription maintenance as audit lifecycles. Meaningful automatic catalog changes produce a bounded `upstream.catalog_changed` fact; strict mode persists the catalog mutation and audit fact in one transaction.
- Preserve protected caller activity, administrative changes and historical records. Background outcomes remain observable through bounded logs and `vmcp_background_operations_total`; system payload settings do not re-enable maintenance auditing.

## Delivery and PostgreSQL

- Wake same-process delivery readers directly after committed writes. Other replicas use durable PostgreSQL polling instead of per-operation delivery `NOTIFY` broadcasts. Configuration snapshot notifications remain enabled.
- Cross-replica GET delivery polls every 250 ms; pending reply/readiness waits use 50 ms polling. Durable replay, session checks, leases and fencing remain in place. Polling intervals are not a hard end-to-end latency guarantee.
- Migration **32** adds delivery cleanup/cascade indexes for streams, pending requests and completed operations.
- Add an isolated MicroK8s benchmark harness with PostgreSQL diagnostics, an optional durable OLTP profile and a sampled 500 ms cross-process polling gate. Raw evidence is locally archived with verified checksums; Git contains curated reports and summaries.

## Container and release security

- Update the Go runtime base to non-root Distroless Debian 13 and the web runtime to Nginx 1.30.6. Pin builder/runtime images and selected deployment dependencies by multi-platform digest.
- Apply read-only filesystems, dropped capabilities, no-new-privileges and bounded temporary mounts to local application Compose services. Retain hardened Helm defaults.
- Scan all nine application images in CI. Before assigning a release tag, scan the exact candidate digest for both Linux AMD64 and ARM64, then sign and verify it with Cosign using the publishing workflow's GitHub OIDC identity.
- Preserve SBOM/provenance and scan evidence. The GitHub release job independently verifies all nine image signatures. Document installation-time signature verification; Helm itself does not enforce cluster admission signatures.
- Add weekly Dependabot updates and build-context exclusions. Update the web `ip-address` dependency to 10.7.4 and gate web CI on high/critical npm audit findings.

## Upgrade and behavior changes

1. Back up the database and encryption recovery keys. Apply migrations through **32** before starting the updated control/data planes. Migration 32 creates indexes using ordinary `CREATE INDEX`; schedule for the size and write activity of existing delivery tables. Its rollback removes those indexes.
2. Upgrade **all** control-plane, data-plane and web instances before enabling mock upstream settings. Refresh affected clients' `tools/list`. Older binaries do not manage mock mappings or apply the mock namespace prefix.
3. Operators consuming system audit streams must account for reduced routine maintenance events. Use the background metrics/logs for poll/reconnect health and the catalog-change audit fact for automatic configuration changes. Existing audit history is retained.
4. Mixed-version replicas can rely on the durable polling path, but complete the rollout to remove old replicas' delivery notification traffic. Do not disable the separate configuration notification channel.
5. Configure a private shared WireMock service only if mocks are required; the deployment examples include a pinned image and restricted runtime settings. Existing non-mock MCP/REST upstreams do not require WireMock.
6. New image signatures apply to this hardened publishing workflow. Older releases may not be signed. Verify the expected repository, workflow and version identity before installation.

The application and packaged Helm chart advance to 1.0.0. This version number does not replace workload-specific capacity, failover, recovery or security validation.

## Validation and measured limits

- Local image validation built all nine application images for AMD64 and ARM64. All 18 scans with Trivy 0.76.1 found no HIGH/CRITICAL findings. Web lint and 250 unit tests, npm audit, Helm rendering tests, archive/reporting tests, release manifest tests and the restricted Compose application smoke passed.
- Targeted Go race/integration tests passed for migration upgrade/rollback, durable routing/replay, replica-local wakes, duplex calls and subscription recovery. GitHub CI additionally gates the complete Go race/integration suite, browser checks, image security and disposable-cluster Helm installation/upgrade before publication.
- The final five-minute local MicroK8s run offered 1,000 TPS and achieved **998.7 successful TPS**, **135.7 ms p95**, **485.4 ms p99**, 3 errors and 358 dropped scheduled calls. All 300,389 successful calls including warmup matched audit admissions/outcomes, with zero duplicates and zero incomplete calls. The separate 24-event polling probe measured **250.363 ms p95 / 256.179 ms max**.
- **Overall high-load acceptance remains failed** because the existing large-catalog post-load key-revocation/snapshot propagation check did not complete within its observation window. This result does not by itself prove that a revoked credential was accepted. It remains an unresolved capacity/freshness limit and must not be represented as a fully passing acceptance run.
- The five-minute run does not establish sustained retention cleanup capacity past the 15-minute delivery TTL. The existing cleanup batch/duty budget and large-catalog refresh behavior require further optimization and longer validation before claiming sustained production 1,000 TPS. PostgreSQL tuning in the report is specific to the isolated local benchmark and is not applied to production deployments.
