# Omni MCP v1.2.0 kabul değerlendirmesi — 27 Ekim 2026

## Sonuç

**1.000 tool / 100 çağrı/s / 10 dakika Omni invocation kabulü geçti.**
60.000 çağrının tamamı doğru sonuçla tamamlandı; hata, düşen istek veya çift
çalıştırma yok. Yük altında runtime key, upstream tool onayı ve Omni yayın iptali
105–107 ms içinde etkili oldu. Yetkisi kaldırılan hedefe sonraki çağrılar kabul edilmedi.

Semantic discovery yükü normal vMCP yolunun gecikmesini ve CPU tüketimini artırdı,
ancak çağrı kabul eşikleri korunuyor. Ayrı embedding modeli bu profilin en pahalı
CPU bileşeni. Arama cevaplarının %0,233'ü açıkça keyword fallback modundaydı;
**bu çalışma kesintisiz 100 semantic arama/s garantisi değildir**.

Makine tarafından okunabilir [yük özeti](omni-1000-100-20261027.json),
[yük altında yönetişim kontrolleri](omni-governance-20261027.json),
[semantic değerlendirme](omni-semantic-20261027.json),
[sağlayıcı teşhisi](omni-provider-diagnostic-20261027.json) ve
[kaynak/imaj/arşiv kimlikleri](omni-provenance-20261027.json) ayrı tutulur.

## Ortam ve kapsam

- İzole, tek düğümlü MicroK8s; mevcut `vmcp-demo` pod UID/restart durumları değişmedi.
- 10 upstream + 10 vMCP, her birinde 100 tool: toplam **1.000 tool**.
  Provider/consumer ekipleri, sahipli proje ve açık tool onayları etkin.
- Bir DP: GOMAXPROCS=2, CPU request=2 / limit=4, GOMEMLIMIT=4GiB,
  pod memory limit=6GiB. Strict audit ve Redis etkin.
- Bir Omni: CPU limit=2, GOMAXPROCS=2, GOMEMLIMIT=512MiB, pod limit=1GiB.
  Metadata/vectors dışında schema veya DB/master-key taşımıyor.
- Trafik: %50 REST ve %50 native MCP; iki tip yaklaşık 50 TPS alıyor.
  Native çağrılar ayrı geçici upstream oturumu açıyor. Host üzerinde sentetik,
  düşük gecikmeli upstream'ler; gerçek uzak servis/TLS gecikmesi modellenmiyor.
- NodePort/CNI yolu; üretim ingress/TLS kapasitesi testi değil. Tekrar deneme yok.
  100 TPS, 100 tam dört-adımlı agent akışı değil, 100 MCP çağrısı anlamına geliyor.
- Aynı v1.2.0 çalışma ağacında Omni kapalı/açık karşılaştırması; v1.1.0 binary A/B
  karşılaştırması veya maksimum TPS araması değil.
- Embedding: yerel, gerçek ONNX `paraphrase-multilingual-mpnet-base-v2`, FastEmbed
  0.9.1; response cache yok. Model host üzerinde, Omni pod limitinin dışında.
  Host 64 mantıksal CPU sunuyor; modelin üretim kaynak bütçesi ayrıca planlanmalı.
- Her yaklaşık 5 saniyede kubelet RSS/usage/CPU, uygulama metrikleri, PostgreSQL
  ve GC logları toplandı. Gözlem yükü ölçüme dahildir; sampled peak sürekli HWM değildir.

## Üç ardışık 10 dakikalık faz

Çağrı eşikleri: ≥99 başarılı TPS, ≥%99,9 başarı, p95≤250 ms, p99≤1 s,
sonuç/nonce/route/PII bütünlüğü ve çift çalıştırma olmaması.

| Faz | Başarılı / gönderilen | Başarılı TPS | p95 | p99 | Hata / düşen |
|---|---:|---:|---:|---:|---:|
| Omni kapalı, doğrudan vMCP | 59.996 / 60.000 | 99,990 | 42,28 ms | 53,18 ms | 4 / 0 |
| Omni `invoke_tool` | 60.000 / 60.000 | 99,998 | 20,70 ms | 24,50 ms | 0 / 0 |
| Doğrudan vMCP + ayrıca 100 discovery/s | 60.000 / 60.000 | 99,993 | 75,78 ms | 115,38 ms | 0 / 0 |

Discovery eşliğinde doğrudan çağrı p95'i yaklaşık %79, p99'u %117 arttı; her ikisi
de eşik altında. Bu ardışık tek koşu bir nedensel/istatistiksel performans garantisi
oluşturmaz. Omni invocation'ın daha düşük gecikmesi, kalıcı direct-MCP delivery/
replay yolunu kullanmamasıyla birlikte değerlendirilmelidir; özellikler aynı değildir.
Native upstream'lerde geçici session maliyeti uzak ağlarda daha yüksek olabilir.

Omni invocation audit'inde REST sunucu içi p95/p99 **13/15 ms**, native MCP
**14/17 ms**. Bunlar HTTP istemci gecikmesiyle aynı ölçüm değildir.
60.000 ölçülen Omni çağrısı + restart sonrası 1 probe için **60.001 başarılı audit
kaydı** var; actor/target/trace alanları eksik değil. Çift execution **0**.

### Discovery ve provider sınırı

Ek discovery fazında **60.004 cevap, sıfır hata/düşen**, p95 **170,25 ms**,
p99 **188,56 ms** ölçüldü. Bağımsız ticker fazın bitişindeki son istekleri de
beklediği için arama sayısı tam 60.000 değil; yaklaşık 100 arama/s.
**59.864 hybrid**, **140 keyword/fallback** (%0,233).
Üretim varsayılanı olan 120 arama/dakika/credential/replica yerine test anahtarında
12.000/dakika kullanıldı. Invocation kotası bununla değiştirilmedi.

Sağlayıcı fixture'ında aynı anda en fazla 16 embedding isteği çalışıyordu.
Ardından yapılan **60 saniyelik doğrudan provider teşhisi**, aynı model ve 100 RPS ile:

| Provider concurrency | HTTP 200 | HTTP 429 | Başarılı istek p95 |
|---|---:|---:|---:|
| 16 | 5.940 | 60 | 168,28 ms |
| 32 | 6.000 | 0 | 154,63 ms |

Provider'ın `busy_429` sayacı HTTP sonuçlarıyla birebir eşleşti. Bu, dar concurrency
sınırının fallback üretebildiğini yeniden gösteriyor. Ana koşunun her fallback'inde
provider status'u ayrı kaydedilmediğinden 140 olayın tamamının tek tek 429 olduğunu
iddia etmiyoruz. 32 sınırıyla **10 dakikalık gateway tekrar testi yapılmadı**;
32/6.000 sonucu kısa provider teşhisidir, ana yük sonucunun yerine geçmez.
Gateway HTTP kullanılabilirliği ile semantic mod kullanılabilirliği ayrı SLO olmalı.

## Bellek, CPU ve GC

| Faz / bileşen | Tepe RSS | Tepe container usage | Ortalama CPU çekirdeği | RSS ilk/son üçte bir medyan değişimi |
|---|---:|---:|---:|---:|
| Direct baseline / DP | 51,75 MiB | 56,23 MiB | 0,326 | +%4,72 |
| Omni invocation / DP | 51,47 MiB | 57,85 MiB | 0,280 | +%0,91 |
| Omni invocation / Omni | 16,30 MiB | 21,76 MiB | 0,133 | +%2,06 |
| Direct + discovery / DP | 57,52 MiB | 64,81 MiB | 1,091 | +%0,06 |
| Direct + discovery / Omni | 25,03 MiB | 36,07 MiB | 1,156 | −%5,52 |

DP'nin 5GiB RSS / 5,4GiB usage bütçelerinden çok uzaktayız. %20 büyüme inceleme
sınırı ölçülen trafik pencerelerinde aşılmadı. İlk driver faz etiketini index
kurulurken de koruduğu için ham baseline etiketi 670 saniye içeriyordu; kaynak
özeti gerçek 600 saniyelik trafik penceresine kırpıldı (5 saniye çözünürlük).
Geçiş örneklerini dahil etmek yanıltıcı +%42,8 büyüme üretiyordu. Tekrarlanabilir
harness artık geçişi `setup` olarak işaretliyor.

Orijinal podların ilk 30 saniyesi hariç, fazlar birlikte GC özeti:

| Bileşen | GC/s | Ortalama GC CPU çekirdeği | p95 STW | En büyük gözlenen canlı heap |
|---|---:|---:|---:|---:|
| DP | 2,47 | 0,0635 | 0,372 ms | 25 Go-MB |
| Omni | 8,49 | 0,0485 | 0,314 ms | 11 Go-MB |

GC sıklığı discovery sırasında artsa da ölçülen CPU/pause maliyeti düşük;
Go bellek hedefini artırmayı gerektiren baskı yok. Model ise yaklaşık **1.545 MiB
tepe RSS**, discovery sırasında yaklaşık **12–14 CPU çekirdeği** kullandı.
Bu kaynaklar Omni'nin 1GiB pod limitine dahil değildir. Model inference maliyeti
ve her aramada taşınan güncel yetki manifestleri, bu profilin başlıca ek maliyetleri.
Yeni bir DB/vector store bu testin parçası değil.

OOM event'i veya beklenmeyen restart bulgusu yok. Arıza kontrolleri deployment'ları
bilerek sıfıra indirip yeniden oluşturdu; son pod restart sayaçları tek başına
kesintisizlik kanıtı sayılmadı, original pod logları ve events de saklandı.

## Yetki, arıza ve işlevsel kabul

- 600 saniyelik invocation fazının ortasında ayrı runtime key iptali:
  ilk 401 **107,45 ms**, ilk 401 sonrasında farklı yanıt **0**.
- Ayrı 30 saniyelik 100 TPS yönetişim senaryosu: **3.000/3.000** doğru çağrı,
  p95 **15,83 ms**, p99 **18,79 ms**. Bir upstream tool onayı **105,25 ms**,
  vMCP Omni yayını **104,87 ms** içinde kaldırıldı. Sonraki 20'şer invoke/discovery
  kontrolünde yetkisiz kabul yok. Yayından kaldırma normal direct vMCP erişimini bozmadı.
- Zorlanan embedding kesintisi açık `keyword-fallback` moduyla çalıştı.
- Omni kapalıyken direct çağrı çalıştı; Omni restart sonrası index yeniden kuruldu
  ve çağrı çalıştı. DP kapalıyken discovery **503** ile fail-closed kaldı.
- Gerçek MCP TypeScript SDK ile dört tool/şema/çağrı; OAuth issuer/audience, claim
  binding, IP kuralları, başka proje/vMCP metadata izolasyonu ve eski schema-version
  reddi Go testleriyle doğrulandı.
- Migration 33 → 34 mevcut vMCP'yi koruyor ve publication=false bırakıyor.
  CI gerçek Helm install → Omni etkin upgrade → direct + Omni çağrılarını çalıştırdı.
- İlk CI smoke hatası, upgrade sırasında pod'a sabitlenmiş `kubectl port-forward`ın
  kapanmasıydı. Test bağlantıları rollout sonrasında yeniden kuracak şekilde düzeltildi;
  uygulama yükseltmesi veya veri kaybı hatası değildi.

Baseline'daki dört MCP hatasının audit nedeni **`authorization changed before dispatch`**.
CP'nin ilk katalog yenilemeleri global revision değiştirdiğinde mevcut güvenlik
kontrolü eski snapshot ile yürüyen çağrıyı reddetti. Bu, yetkisiz çağrı kabulü değil;
önceki sürümde belgelenen davranış devam ediyor. Guard kaldırılmadı, otomatik write
retry eklenmedi. Diğer iki 10 dakikalık çağrı fazında hata yok.

## Semantic kalite

1.000 tool içinde 30 İngilizce tool açıklaması ve 60 etiketli intent (30 EN/30 TR),
970 sentetik operasyonel istatistik tool'u ile test edildi. İlk küçük modelde
lexical substring eşleşmesi ve eşit ağırlıklar yanıltıcı sonuçlar üretti; tam sözcük
ve semantic ağırlıklı skorla düzeltildi. Aynı model yine Türkçe eşiğin altında kaldı.

| Gerçek model / skor | EN recall@5 | TR recall@5 |
|---|---:|---:|
| multilingual MiniLM / ilk skor | 28/30 | 25/30 |
| multilingual MiniLM / düzeltilmiş skor | 28/30 | 26/30 |
| multilingual MPNet / düzeltilmiş skor | **29/30 (%96,7)** | **28/30 (%93,3)** |

Son model iki dilde de %90 eşiğini geçti. Bu küme geliştirme sırasında incelendi;
held-out kurum verisi değildir. Üretim arama kalitesi için ayrı, kuruma özgü
etiketli değerlendirme gerekir. Ürün model/provider seçimini operatöre bırakır.
